# Образец задания для ГИА ДЭ ПУ (инвариантная часть)
## Вариант 09. Магазин строительных материалов «СтройБаза»

**Общее время выполнения — 4 часа:** Модуль 1 — 50 минут, Модуль 2 — 40 минут, Модуль 3 — 1 час 40 минут, Модуль 4 — 50 минут.
Описание предметной области (Приложение 1), данные для импорта (Приложение 2, папка `data`) и руководство по стилю (Приложение 3) входят в состав этого задания.

## Задание

Компания «СтройБаза» реализует строительные материалы: сухие смеси, лакокрасочные материалы, крепёж и инструмент. Очень важно постоянно получать актуальную информацию об остатках материалов на складах, поэтому необходимо реализовать следующие модули.

При запуске приложения окно входа – первое, что видит пользователь. На ней пользователю предлагается ввести свой логин и пароль, взятый из базы данных,
или есть возможность перейти на экран просмотра материалов (без фильтрации, сортировки, поиска) в роли гостя.

Только после удачной авторизации пользователь получает доступ к остальным модулям системы:

- гость может просматривать материалы (без фильтрации, сортировки, поиска);
- авторизованный клиент (роль «Покупатель») может просматривать материалы (без фильтрации и сортировки, без поиска);
- менеджер (роль «Кладовщик») может просматривать материалы (с фильтрацией, сортировкой, поиском), просматривать заказы и изменять количество на складе у материалов (поле «Остаток на складе»), остальные данные материалов менять не может;
- администратор (роль «Администратор») может просматривать (с фильтрацией, сортировкой, поиском), добавлять, редактировать и удалять материалы, просматривать, добавлять, редактировать и удалять заказы.

Подробная таблица прав — в Приложении 1.

## Модуль 1. Разработка, администрирование и защита баз данных (50 минут)

**Задание:**

1. На основе описания предметной области (Приложение 1) создайте базу данных в СУБД SQL Server для разрабатываемой системы.
   Обязательна 3 нормальная форма с обеспечением ссылочной целостности. При разработке базы данных обратите внимание на согласованную схему именования,
   создайте необходимые первичные и внешние ключи, ограничения (например, на недопустимые значения цены, остатка и скидки).
2. Получите ER-диаграмму средствами СУБД или ПО для построения и редактирования диаграмм (UML) и блок-схем. ER-диаграмма должна быть представлена в формате PDF
   и содержать таблицы, связи между ними, атрибуты и ключи (типами данных на данном этапе можно пренебречь).
3. Заказчик системы предоставил файлы с данными (Приложение 2, формат CSV) для переноса в новую систему. Необходимо подготовить данные файлов для импорта
   и загрузить в разработанную базу данных. Номера и значения из файлов не должны изменяться.
4. Сохраните полученные результаты: создайте скрипт БД (файл .sql), включающий создание таблиц, ролей и загрузку данных.

Необходимые приложения: Приложение 1, Приложение 2 (файлы `data/*.csv`).

**Инструкции для ГЭ:** при выполнении заданий участникам ДЭ запрещён доступ в Интернет, за исключением разового доступа в зоне общего (коллективного) пользования
в течение не более 15 минут. Это время включается во время выполнения заданий модулей ДЭ. Доступ может осуществляться для получения справочной информации, необходимой в процессе разработки, без использования авторизации на сайтах. Во время работы с Интернетом запрещается использовать сетевые диски, мессенджеры, ресурсы с генеративными способами формирования текста, репозитории, сайты вопросов и ответов для программистов, социальные сети.
Контроль за компьютером осуществляется экспертами с помощью удалённого доступа.

## Модуль 2. Разработка модулей программного обеспечения для компьютерных систем (40 минут)

**Задание:**

Создайте формы приложения (Windows Forms, C++/CLR) **без бизнес-логики**: на этом этапе необходимо разместить элементы интерфейса, настроить их свойства и оформление.
Компоненты системы должны иметь единый согласованный внешний вид, соответствующий руководству по стилю, представленному в Приложении 3.
Заголовок окна должен соответствовать назначению. Установите иконку приложения и логотип компании на главной форме (из ресурсов).
Оформление кода: идентификаторы должны отражать их назначение; допустимо использование не более одной команды в строке.

Необходимо создать следующие формы.

**2.1. Окно входа.** Поля «Логин» и «Пароль» (символы пароля скрыты), кнопки «Войти» (кнопка целевого действия, цвет акцентирования) и «Войти как гость», логотип.

**2.2. Окно списка материалов.** Состав окна:

- шапка (дополнительный фон): логотип, поле поиска, выпадающий список фильтра, выпадающий список сортировки, ФИО пользователя в правом верхнем углу, кнопка «Выйти»;

- область прокрутки со списком карточек.

на этапе Модуля 2 цвета проверяются на тестовых карточках (по одной на каждое правило подсветки).

Выпадающий список фильтра: «Все поставщики», далее значения поля «Поставщик». Выпадающий список сортировки содержит варианты: «Без сортировки», «Остаток: по возрастанию», «Остаток: по убыванию».

**2.3. Форма добавления / редактирования материала.** Поля формы:

|:-:|---|---|

| 3 | Категория материала | выпадающий список |

## Модуль 3. Сопровождение и обслуживание программного обеспечения компьютерных систем (1 час 30 минут)

**Задание:**

**3.1. Алгоритм.** Сформируйте алгоритм работы приложения (от запуска до завершения, включая авторизацию, просмотр списка, редактирование материала и работу с заказами).
Оформите алгоритм в виде блок-схемы согласно стандарту ГОСТ 19.701-90. Документ представьте в формате .pdf.

**3.2. Архитектура логики.**

- Бизнес-логика реализуется на языке C++ в виде **отдельного модуля** (библиотеки), который ничего не знает ни о базе данных, ни об интерфейсе
  (не подключает заголовки и библиотеки СУБД и WinForms, не использует типы `System::`).
- Всё, что логике нужно от внешнего мира (чтение и сохранение данных, хранение изображений), описывается интерфейсами (абстрактными классами) модуля;
  их реализации будут подключены на этапе интеграции.
- Для данных используются стандартные типы C++ (строки `std::wstring`, целые числа, деньги — в копейках целым числом, даты — собственной структурой).
- Модуль имеет единый программный интерфейс (API) для взаимодействия с остальными слоями.

**3.3. Реализуйте в логике:**

1. Авторизацию и права ролей (таблица прав в Приложении 1): любое действие, на которое у роли нет права, завершается ошибкой «недостаточно прав».
2. Подготовку данных для списка материалов: итоговая цена, вид подсветки карточки, путь к изображению (или признак «изображения нет»).
3. Поиск, фильтрацию и сортировку списка (совместно, по правилам из Приложения 1).
4. Добавление и редактирование материала с проверкой ввода; обработку изображения по правилам из Приложения 1 (в том числе откат при сбое сохранения и удаление старого файла только после успешной записи).
5. Удаление материала с учётом ограничений.
6. Добавление, редактирование и удаление заказов: разбор состава заказа, проверки и ограничения из Приложения 1.
7. Обработку исключительных ситуаций: ошибки ввода (с перечислением всех найденных ошибок сразу), нарушение правил предметной области, отсутствие прав, сбой хранилища.
   Текст сообщения должен быть полезным и информативным, содержать полную информацию об ошибке пользователя и порядок действий для её исправления.

**3.4. Проверка.** Напишите консольную программу или набор тестов, которая запускает логику на тестовых данных с «поддельным» хранилищем в памяти (без базы данных и без интерфейса)
и проверяет не менее 10 ситуаций, включая: расчёт итоговой цены, каждое правило подсветки, комбинацию поиска, фильтра и сортировки, отказ при отсутствии прав,
запрет удаления, отклонение неверного ввода.

**3.5. Оформление кода.** Идентификаторы отражают назначение и соответствуют единому соглашению об именовании; допустимо не более одной команды в строке.
Необходимо использовать комментарии для пояснения неочевидных фрагментов кода: комментарии должны присутствовать только в местах, которые требуют дополнительного пояснения.

Необходимые приложения: Приложение 1.

## Модуль 4. Осуществление интеграции программных модулей (1 час)

**Задание:**

**4.1. Преобразование данных.** Реализуйте слой согласования между логикой (стандартные типы C++) и управляемой средой интерфейса:
строки `std::wstring` ↔ `String^`, деньги (копейки) ↔ `Decimal`, даты ↔ `DateTime`, исключения логики → исключения управляемой среды, данные списков → объекты для привязки к формам.
Интерфейс должен обращаться к логике только через этот слой.

**4.2. Подключение базы данных.** Реализуйте интерфейсы хранилища, описанные в логике, поверх созданной базы данных (Модуль 1). Приложение подключается к БД
под учётной записью, соответствующей роли вошедшего пользователя (гость и клиент, менеджер, администратор). Параметры подключения не должны быть «зашиты» в код.

**4.3. Привязка логики к формам.** Подключите логику к формам Модуля 2: вход и гостевой вход, список материалов с подсветкой, поиск, фильтр и сортировка в реальном времени,
форма добавления / редактирования материала, удаление, список заказов и форма заказа. Состав элементов на формах зависит от роли (таблица прав в Приложении 1).

**4.4. Последовательный интерфейс.** Настройте порядок появления форм:

- первой всегда открывается окно входа; после успешной авторизации или входа гостем открывается список материалов;
- из списка доступны переходы: «Заказы» (для ролей с правом просмотра заказов), форма добавления (кнопка «Добавить материал»), форма редактирования (при нажатии на конкретный элемент списка);
- из каждого окна есть возврат назад (кнопка «Назад» или закрытие окна); выход из учётной записи возвращает на окно входа; ФИО пользователя отображается в правом верхнем углу;
- невозможно открыть более одного окна редактирования одновременно;
- после добавления, редактирования и удаления данные в окне списка обновляются.

**4.5. Сообщения пользователю.** Пользователь уведомляется о совершаемых им ошибках, о запрещённых в рамках задания действиях, о неотвратимых операциях (подтверждение удаления).
Окна сообщений соответствующих типов (ошибка, предупреждение, информация) отображаются с соответствующим заголовком и пиктограммой.

**4.6. Отладка.** Выполните отладку приложения для проверки функциональности: приложение должно корректно работать и не должно происходить аварийного завершения работы.
Создайте документ docx и вложите в него скриншоты корректной работы системы: вход (успешный и неуспешный), список для каждой роли, поиск + фильтр + сортировка,
добавление и редактирование материала, запрет удаления, список заказов и форма заказа, примеры сообщений об ошибках.

Все практические результаты должны быть переданы путем загрузки файлов на предоставленный репозиторий системы контроля версий.

**Практические результаты:**

# Приложение 1. Описание предметной области

## 1.1. Роли пользователей и права

| Действие | Гость | Покупатель | Кладовщик | Администратор |
|---|:-:|:-:|:-:|:-:|
| Просмотр списка материалов | ✓ | ✓ | ✓ | ✓ |
| Поиск по списку | — | — | ✓ | ✓ |
| Сортировка списка | — | — | ✓ | ✓ |
| Фильтрация списка | — | — | ✓ | ✓ |
| Просмотр собственных заказов | — | — | — | — |
| Просмотр всех заказов | — | — | ✓ | ✓ |
| Добавление, редактирование и удаление материалов | — | — | — | ✓ |
| Изменение только поля «Остаток на складе» | — | — | ✓ | ✓ |
| Добавление, редактирование и удаление заказов | — | — | — | ✓ |
| Изменение только статуса заказа | — | — | — | ✓ |

Администратору доступно редактирование всех полей, поэтому строки «Изменение только …» для него отмечены как частный случай полного права.
Роли пользователей в системе: «Администратор», «Кладовщик», «Покупатель»; не прошедший вход пользователь работает как «Гость».

## 1.2. Данные системы

- **Пользователь:** ФИО, логин (уникален), пароль, роль.
- **Материал:** внутренний числовой идентификатор (ID) — при добавлении вычисляется автоматически как следующий за имеющимся в БД, при редактировании только для чтения;
  артикул (уникален); наименование; категория материала; производитель; поставщик; единица измерения; цена; действующая скидка (%);
  остаток на складе; описание; фото (путь к файлу изображения).
- **Справочники:** категория материала, производитель, поставщик, единицы измерения, статусы заказов, роли.
- **Склады выдачи:** номер и адрес.
- **Заказ:** номер; состав (набор позиций «артикул — количество»); статус; склад выдачи; дата заказа; дата доставки; клиент; код для получения.

## 1.3. Бизнес-правила

1. **Итоговая цена.** Итоговая цена материала = цена × (100 − действующая скидка) / 100, округление до копеек. Если скидка больше нуля, в карточке основная цена перечёркнута (цвет шрифта красный, #FF0000), рядом выводится итоговая цена (цвет шрифта чёрный); если скидки нет — выводится одна цена чёрным цветом.
2. **Подсветка карточек.** Цвет фона карточки определяется первым выполненным условием из списка:
   1. материал отсутствует на складе (остаток равен 0) — фон голубой (#B3E5FC);
   2. размер действующей скидки превышает 10 % — фон лаймовый (#DCE775).
   Если ни одно условие не выполнено, используется основной фон.
3. **Поиск** выполняется по всем текстовым полям материала (Артикул, Наименование, Категория материала, Описание, Производитель, Поставщик, Единица измерения); допускается ввод нескольких слов — каждое слово должно встретиться хотя бы в одном из полей; регистр букв не учитывается.
4. **Сортировка** по полю «Остаток на складе» (по возрастанию и по убыванию).
5. **Фильтрация** по полю «Поставщик»; первым элементом выпадающего списка является «Все поставщики», при выборе которого фильтр сбрасывается.
6. **Совместная работа.** Поиск, фильтрация и сортировка выполняются в реальном времени (без кнопок «найти» и «применить») и действуют одновременно; ранее выбранные параметры не сбрасываются при изменении остальных.
7. **Удаление.** Нельзя удалить материал, если материал присутствует в заказе или остаток на складе больше нуля.
8. **Изображение.** Размер изображения ограничен 300×200 пикселей (большие изображения уменьшаются с сохранением пропорций). Загруженное изображение сохраняется в папку приложения, в базе данных хранится путь к нему; при замене изображения старый файл удаляется. Если изображения нет, выводится картинка-заглушка (picture.png).
9. **Проверка ввода материала.** Допустимыми считаются значения: цена — число не меньше нуля, не более двух знаков после запятой; «Остаток на складе» — целое число не меньше нуля; скидка — целое число от 0 до 100; артикул и наименование обязательны, артикул уникален (регистр и кириллические двойники латинских букв не учитываются); «Категория материала», «Производитель», «Поставщик» и «Единица измерения» выбираются из справочников.
10. **Заказ.** Состав заказа задаётся в формате «артикул, количество, артикул, количество»: артикулы должны существовать в базе, количества — целые числа больше нуля, один артикул не может повторяться в заказе. Код для получения назначается системой автоматически и уникален. Заказ содержит: состав, статус, склад выдачи (адрес), дату заказа, дату доставки, клиента. Дата доставки не может быть раньше даты заказа.
11. **Контроль остатков.** При сохранении заказа количество каждой позиции не должно превышать остаток этой позиции на складе; при нарушении выводится сообщение с наименованием позиции и доступным остатком.
12. **Остатки.** Для роли «Кладовщик» на форме редактирования материала доступно только поле «Остаток на складе»; остальные поля только для чтения, кнопки «Добавить материал» и «Удалить» не отображаются.

# Приложение 2. Файлы данных для импорта

| Файл | Содержимое | Записей |

Формат файлов: кодировка UTF-8, разделитель полей «;», первая строка — заголовки, даты в формате дд.мм.гггг (файлы получены выгрузкой из Excel «CSV UTF-8»).
Данные корректны; импортировать их нужно без искажения содержимого.

**`products.csv`** — перечень материалов:

| № | Поле | Примечание |
|:-:|---|---|
| 1 | Артикул | строка из 6 символов (латиница и цифры), уникальна |
| 2 | Наименование |  |
| 3 | Единица измерения | значение справочника |
| 4 | Цена | целое число рублей |
| 5 | Поставщик | название организации (справочник) |
| 6 | Производитель | справочник |
| 7 | Категория материала | справочник |
| 8 | Действующая скидка | целое число, проценты |
| 9 | Остаток на складе | целое число ≥ 0 |
| 10 | Описание | текст |
| 11 | Фото | имя файла изображения из папки ресурсов; пусто — изображения нет |

**`users.csv`** — поля: Роль, ФИО, Логин, Пароль. Роли: «Администратор», «Кладовщик», «Покупатель». ФИО уникальны.

**`pickup_points.csv`** — поля: Номер, Адрес. Номер используется в заказах для ссылки на склад выдачи.

**`orders.csv`** — поля: Номер заказа; Артикул заказа; Дата заказа; Дата доставки; Номер пункта выдачи; ФИО клиента; Код для получения; Статус заказа.
В поле «Артикул заказа» через запятую перечислены пары «артикул, количество» (например, `A112T4, 2, F635R4, 1`): одна ячейка содержит несколько позиций,
поэтому при проектировании базы состав заказа необходимо привести к нормальной форме. Клиент в заказе указан по ФИО; номер пункта выдачи ссылается на `pickup_points.csv`.

Статусы заказов, встречающиеся в данных: «Новый», «Комплектуется», «Завершен».

**Ресурсы** (выдаются организаторами вместе с заданием, в файлы CSV не входят): логотип `logo.png`, значок приложения `icon.ico`, картинка-заглушка `picture.png`,
фотографии `1.jpg`, `2.jpg`, … (имена указаны в поле «Фото»).
